Second-Order SQL Injection

This profile editor sanitizes nothing on save — but nothing dangerous happens on save either. The payload sits quietly in the database until a different request trusts it and builds a query with it. Input sanitization at one layer never protects a value that gets re-used at another.

STEP 1 — SAVE A DISPLAY NAME

Update your profile. Nothing is queried with this value on save.

STEP 2 — VIEW A PROFILE

This page builds a query from the stored display name.

CHALLENGES
01 — Make the second query errorSave a display name that breaks the profile query. Nothing happened on save — that's the point.
02 — Leak the users tableUse the stored payload to UNION in the admin's password when the profile page runs.
03 — Become adminYour stored value reaches an UPDATE that sets role. Turn alice into an admin.
View solutions
01 — Break the second query A single quote stored on save, detonated on view. 
Display name: O'Brien

The view query becomes WHERE name = 'O'Brien' — unterminated string, SQL error. No sanitization happened at save time.

02 — Leak the password Payload stored now, fired later, UNIONed in when the profile page runs. 
Display name: x' UNION SELECT id, name, password, role FROM users WHERE name='admin' --
03 — Privilege escalation The stored value reaches a role-update statement. 
Display name: x', role='admin' WHERE name='alice' --

On save, the app builds UPDATE users SET name='<input>' WHERE id=<id>. Your payload turns that into a second statement that also flips the role.
