Key Takeaways

You found a way in. Here's what actually happened — and why it matters beyond this lab.

01 — WHAT JUST HAPPENED

The login form built its SQL query by pasting your input directly into the query text. It never asked "is this a value, or is this code?" — it just glued strings together.

The application intended this:

SELECT id, name, role FROM users
WHERE name = 'ahmed' AND password = 'wrong'

But when you typed admin' --, it became: 

SELECT id, name, role FROM users
WHERE name = 'admin' --' AND password = 'wrong'

The database doesn't see "a username". It sees a string that ends early, followed by a comment. Everything after -- is thrown away — including the password check.

02 — WHY THE DASHES WORK

In SQL, -- means "ignore the rest of this line". It's a comment marker, just like // in JavaScript or # in Python.

So the database only ever evaluates this part of the query: 

SELECT id, name, role FROM users
WHERE name = 'admin'

No password condition. No second check. It finds the admin row and returns it — and the application happily treats that as a successful login.

The core insight: your input stopped being data and became code. That is the entire vulnerability, in one sentence.
03 — WHY IT'S DANGEROUS

This isn't just about skipping a password on one form. Once an attacker can rewrite the query, the consequences scale with whatever the database user is allowed to do.

  • Authentication bypass — log in as anyone, including admins, without credentials. (This lab.)
  • Data theft — UNION SELECT can pull data from any table: password hashes, private messages, API keys, customer records.
  • Data destruction — '; DROP TABLE users; -- deletes entire tables in one request.
  • Privilege escalation — write a row into the admins table and you've created a permanent backdoor account.
  • Full server takeover — in misconfigured databases, an attacker can read files or run OS commands through SQL.

SQL injection has been in the OWASP Top 10 for over two decades. It's not exotic — it's the single most common serious web vulnerability, and it's entirely preventable.

04 — THE THREE MISTAKES

Three separate bad decisions had to happen together for this exploit to work. Fixing any one of them would have stopped it.

  1. String concatenation. User input was glued directly into the query instead of being passed as a parameter.
  2. No input validation. A username containing ' and -- is not a username — it should have been rejected before it ever reached the database.
  3. Verbose error messages. When the query broke, the app printed the raw SQL error to the browser. That's a free map of the database for an attacker.
05 — HOW TO FIX IT

Parameterized queries (also called prepared statements). The query structure is defined first, and the user's input is sent separately — so it can never be interpreted as code.

Vulnerable version:

const sql = "SELECT id, name, role FROM users " +
            "WHERE name = '" + user + "' " +
            "AND password = '" + pass + "'";

Safe version:

const sql = "SELECT id, name, role FROM users " +
            "WHERE name = ? AND password = ?";
db.query(sql, [user, pass]);

Same query. Same result for legitimate users. But now admin' -- is treated as a literal string — a username that simply doesn't exist. The injection is structurally impossible, not just filtered out.

Rule of thumb: never build SQL by joining strings. If your query text changes based on user input, you're doing it wrong.
06 — THE MENTAL MODEL

Data should never be able to become code.

That's the pattern behind SQL injection, XSS, command injection, path traversal, template injection — the entire injection family. Different syntax, same bug: untrusted input crosses the boundary from "value" into "instruction".

When you write code that mixes user input with anything that has a grammar — SQL, HTML, shell, file paths — ask yourself: could this input change the structure of what I'm building? If the answer is yes, you need parameterization, escaping, or a strict allowlist. Not a blacklist. Not a "sanitize" function someone wrote on Stack Overflow.

Next time you see a login form: ask where the query comes from. If you can't answer, assume it's concatenated.
