Key Takeaways

Lab 01 was about skipping a check. Lab 02 is about reading data you were never meant to see — the same bug, a different goal.

01 — WHAT JUST HAPPENED

The search box pastes your text directly into the query. The application intended this: 

SELECT name, price, public FROM products
WHERE name LIKE '%keyboard%' AND public = 1

But when you typed ' --:

SELECT name, price, public FROM products
WHERE name LIKE '%' --%' AND public = 1

The ' closes the string, leaving LIKE '%' — which matches every product. The -- then comments out the rest of the line, deleting the AND public = 1 filter entirely. Hidden products come back with the public ones.

02 — WHY THE FILTER FAILED

The filter public = 1 was a hard-coded condition inside the query. It wasn't a separate check. It wasn't enforced by the database. It was just text — and text can be commented out.

The core insight: anything the query says can be un-said by the next input. Row-level access must be enforced by the database itself (views, roles, row-level security), not by string filters.
03 — WHY IT'S DANGEROUS

Lab 01 let you log in. That's bad. But it only gave you the shape of the app's response — "yes" or "no".

Lab 02 gives you a viewer into the database. The LIKE clause is a perfect injection point because the results are printed back to you. Anything a hidden row contains is now on your screen.

  • Visibility bypass — hidden, unpublished, or embargoed products become public. (This lab.)
  • Data exposure at scale — in a real store, "products" often carries internal fields: cost, margin, supplier IDs, stock levels, sometimes draft copy or private notes.
  • The same trick, wider scope — swap the table name and the identical ' -- reads users, orders, invoices, or anything else the database user can see.
  • No error needed — this payload is silent. The page looks normal, just with more rows. Nobody notices in logs.
04 — THE THREE MISTAKES
  1. Concatenation. WHERE name LIKE '%" + v + "%' — the search term is glued into the SQL text.
  2. Security logic in the query string. public = 1 looks like an authorization check, but it's just a filter — trivially removable by an attacker.
  3. Verbose errors. The app prints raw SQL errors back to the browser, telling the attacker exactly what to fix. Even when the payload works silently, the errors help shape the next attempt.
05 — HOW TO FIX IT

Vulnerable:

const sql = "SELECT name, price, public FROM products " +
            "WHERE name LIKE '%" + v + "%' AND public = 1";

Safe — parameterized, with the wildcards inside the parameter: 

const sql = "SELECT name, price, public FROM products " +
            "WHERE name LIKE ? AND public = 1";
db.query(sql, ["%" + v + "%"]);

Now ' -- is treated as literally the string %' --% — a search term that matches no real product. The injection is structurally impossible, not filtered out.

Rule of thumb: if a value needs to be wrapped (in %, quotes, brackets, tags), wrap it in the parameter, never in the query text.
