Data Exfiltration

A public profile viewer. It only returns the name of a user by ID — but if you can reshape the query, you can read columns the developer never intended to expose.

CHALLENGES
01 — Discover the column count The query returns exactly one column. Try UNION SELECT with different column counts and read the error carefully.
Try it in the Profile Viewer tab. Watch the SQL log to see the query change.
02 — Leak the password column Once the column count matches, replace the returned column with password from the users table.
03 — Leak only the admin's password Add a condition so the leaked row is the one you actually want.
View solutions
01 — Find the column count The base query returns exactly one column. 
User ID: ' UNION SELECT 1 --

The error will tell you if the column counts don't match. Adjust the number of values until it accepts them.

02 — Leak the password column Replace the returned column with the sensitive one. 
User ID: ' UNION SELECT password FROM users --

You now get one row per user, with the password field rendered where the profile name used to be. In this mock they're plain strings; in a real app that column might hold hashes, tokens, or nothing sensitive at all — the point is that you chose what the page displays.

03 — Target a specific account Filter the leaked rows so only the admin comes back. 
User ID: ' UNION SELECT password FROM users WHERE role = 'admin' --

This lab's simplified engine doesn't support || string concatenation, so leaking multiple columns in a single cell isn't possible here — one column per query is the intended path.

Key Takeaways

Labs 01 and 02 taught you to skip a check and reveal a row. Lab 03 teaches you to redirect the output — to point the query at columns it was never written to return.

01 — WHAT JUST HAPPENED

The viewer pastes your ID into a query that returns exactly one column. The application intended this: 

SELECT name FROM users WHERE id = '2'

But when you typed ' UNION SELECT password FROM users --: 

SELECT name FROM users WHERE id = '' UNION SELECT password FROM users --'

The first ' closes the ID string, the UNION SELECT appends a second result set to the first, and the -- comments out the leftover quote. The database happily returns the password column in the slot the page was going to print as "name".

02 — WHY UNION WORKS

UNION is a normal SQL feature: it merges the rows of two SELECT statements into one result set. The database doesn't care that the second statement came from user input — it only checks that both sides return the same number of columns.

That's why challenge 01 is "find the column count": once you know the shape, you can slot any column you want into it, from any table the database user can read.

The core insight: you're not breaking the query — you're extending it. The app asked for one column, and you politely handed it a different one.
03 — WHY IT'S DANGEROUS

Labs 01 and 02 gave you a boolean ("did it match?") and a visibility toggle. Lab 03 gives you a print channel — a place on the page where any value you ask for will appear.

  • Credential theft. UNION SELECT password FROM users dumps every password in the table. (This lab.)
  • Schema discovery. In a real database, information_schema.tables lists every table and column — a map of the entire system, obtained the same way.
  • Cross-table reach. The original query only ever touched users. Your payload can read orders, payments, sessions, anything the DB user is allowed to see.
  • Silent and repeatable. No visible error, no alert — a scraper can run this thousands of times and reconstruct the whole database.

This is the classic "in-band" SQL injection technique. It's the fastest and most damaging form, and it's why search bars and profile lookups are favourite targets.

04 — THE THREE MISTAKES
  1. Concatenation. The ID is glued into the query text instead of being bound as a parameter. This is the same root cause as Labs 01 and 02.
  2. Trusting a single column as a boundary. The developer assumed "the query returns one column, so there's nothing to leak." UNION makes that assumption meaningless.
  3. No least privilege. The web app's DB user can read the password column and every other table. If it only had SELECT(name) on a public view, the leak would be impossible even with the injection.
05 — HOW TO FIX IT

Vulnerable:

const sql = "SELECT name FROM users WHERE id = '" + id + "'";

Safe — parameterized:

const sql = "SELECT name FROM users WHERE id = ?";
db.query(sql, [id]);

With a bound parameter, ' UNION SELECT password FROM users -- is treated as literally the string that was typed into the ID field. The database looks for a user whose ID is that exact nonsense string, finds nobody, and returns an empty result. The UNION keyword never reaches the parser.

And a second layer, always worth adding:

// public_view exposes only the columns the public needs
GRANT SELECT (id, name) ON public_view TO web_app;
-- The password column is not even reachable by the web app's DB user.
Rule of thumb: parameterize the query and restrict what the DB user can read. Either one stops this lab; together they stop the whole class.
