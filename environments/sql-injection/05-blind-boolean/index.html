Blind Boolean-Based Injection

This reset-code checker never shows you any data — just a VALID or INVALID badge. Real attackers don't need data in the response to steal it: they need a yes/no question. Watch how far one bit of signal goes.

RESET CODE CHECK

The server only ever answers VALID or INVALID. It never returns a row.

CHALLENGES
01 — Force a VALID resultProve you can flip the oracle's answer without knowing the real code.
02 — Confirm a guessed admin passwordTurn the VALID/INVALID oracle into a yes/no test against the accounts table — the admin's password is R00t!Pass, but pretend you don't know that and verify it blind.
03 — Binary-search a hidden numberWithout ever seeing it, narrow down the admin's 6-digit mfa_secret using greater-than / less-than questions.
View solutions
01 — Force VALID A classic always-true tail turns any input into a match. 
Reset code: ' OR '1'='1

Confirms the input reaches the query logic at all — step one of any blind attack.

02 — Blind password confirmation UNION in a second condition; VALID means the guess was right. 
Reset code: x' UNION SELECT 1 FROM accounts WHERE email='admin@corp.com' AND password='R00t!Pass' --

Change the password guess and the badge flips to INVALID. In a real attack this single query gets retried automatically, thousands of times, by a script — not typed by hand.

03 — Binary search via inequality No data ever appears, yet the secret's value still leaks, one comparison at a time. 
Reset code: x' UNION SELECT 1 FROM accounts WHERE email='admin@corp.com' AND mfa_secret > 200000 --

VALID tells you the secret is above 200000. Keep halving the range (try 300000, then 250000, and so on) and you converge on the exact 6-digit code in under 20 questions — the same technique real blind-SQLi tooling automates.
